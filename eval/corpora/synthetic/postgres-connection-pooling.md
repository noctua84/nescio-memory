---
name: Postgres connection pooling limits and why we moved the pooler
description: Why the per-pod SQLAlchemy pool was replaced with a shared transaction-mode pooler, what the arithmetic was, and the two failure modes that forced the change.
type: decision
---
The original sizing was done per pod and never per cluster, which is the mistake that eventually took the service down twice in one quarter. Each pod opened a pool of twenty connections with a configured overflow of ten, so thirty was the real ceiling per replica rather than the twenty everyone quoted in planning. At eighteen replicas during peak that is five hundred and forty connections against a server configured for four hundred, and the only reason it did not fail immediately is that the overflow connections are opened lazily and most pods never reached their ceiling at the same moment. The first outage happened when a slow downstream call made every request hold its connection for longer, which pushed every pod into overflow simultaneously.

The second failure mode was subtler and took much longer to diagnose. Idle connections are not free on the server side even when they are doing nothing: each one is a backend process with its own work memory allocation, and the planner's memory accounting does not know that most of them will never run a query. We were seeing the resident set grow steadily through the day with no corresponding growth in traffic, and the temptation was to read that as a leak in the application. It was not. It was several hundred idle backends each holding a few megabytes that they had touched once during a sort earlier in their life and never released.

Moving to a transaction-mode pooler in front of the database fixed both at once, because the application's pool size stops being a statement about server backends and becomes a statement about concurrency only. The client pools can now be generous without that generosity reaching the server, and the server sees a stable number of backends regardless of how many replicas are running. The cost is real and worth stating: transaction mode breaks anything that depends on session state surviving between statements, which in practice means prepared statements, advisory locks held across calls, and any use of a temporary table that outlives its transaction.

We audited for all three before cutting over. Prepared statements were the only genuine conflict and were handled by disabling the driver's statement cache, which cost a measurable but acceptable amount of planning time on the hottest queries. Advisory locks were used in exactly one migration helper, which now takes its lock and does its work inside a single transaction. No code used temporary tables. The thing to remember if you are adding code here is that any new dependency on session state will work perfectly in local development, where there is no pooler, and fail intermittently in production under load.
