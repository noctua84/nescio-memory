---
name: Cache stampede mitigation and why we rejected simple locking
description: What happens when a hot key expires under load, the three mitigations considered, and why probabilistic early recomputation was chosen over a mutex or a queue.
type: decision
---
When a popular cache entry expires, every request that wanted it misses simultaneously and every one of them recomputes the same value. The recomputation is expensive, which is why it was cached, so a single expiry can put hundreds of identical expensive operations onto the backend within a few milliseconds. The backend slows down under that load, which makes each recomputation take longer, which means more requests arrive and miss before the first one finishes. We have taken the origin database down this way twice, both times on a key that was so reliably warm that nobody thought of it as a cache dependency at all.

The first mitigation considered was a lock around recomputation: the first request to miss takes a lock and does the work, everyone else waits for it and reads the result. This is correct and it is what most people reach for. We rejected it because the waiting is the problem. Hundreds of requests parked on a lock are hundreds of held connections and hundreds of latency observations at whatever the recomputation cost is, so the backend is protected by moving the queue into the application tier rather than by removing it. If the recomputation takes two seconds, every one of those requests takes two seconds, and under enough concurrency the application tier runs out of workers before the lock is released. It also introduces the question of what to do when the lock holder dies, which means a lock timeout, which means a stampede again whenever the timeout is reached.

The second option was to serve stale data while recomputing in the background: a miss returns the expired value immediately and schedules a refresh. This is a good pattern and we use it in one place where staleness is genuinely harmless. We did not adopt it generally because it requires the cache to retain values past their expiry, which means the expiry no longer bounds how old a served value can be, and reasoning about correctness downstream becomes much harder. There is also a cold start hole: the very first population of a key has no stale value to serve, so the stampede protection is absent exactly when the system is least warm.

What we chose is probabilistic early recomputation. Each read computes whether to refresh the entry based on how close it is to expiry, how expensive the last recomputation was, and a random factor, so refreshes are spread out across the window before expiry rather than bunched at it. The effect is that a hot key is almost always refreshed by a single request well before it expires, and the expiry is reached only by keys that stopped being read. It needs no lock, no coordination between application instances, and no stale serving, and the only state it requires beyond the value is the recomputation duration stored alongside it.

The parameter to be careful with is the aggressiveness factor, which scales how early refreshes start. Set it too high and a hot key is refreshed far more often than it needs to be, which is a steady load rather than a spike but is still load. Set it too low and the spread is too narrow to prevent the bunching. We tuned it by measuring origin request rate per key and raising it until the expiry-time spike disappeared from the graph.
