---
name: Approximate vector index recall and the post-filter trap
description: How an approximate nearest-neighbour index interacts with a tenant filter applied after the candidate window, why that silently returns short result sets, and what actually fixes it.
type: reference
---
The behaviour that caught us is not a bug in the index and it is not a bug in the query. It is what happens when an approximate index produces a fixed-size candidate window and a filter is applied to those candidates afterwards rather than during the walk. The index is asked for its best few hundred candidates by distance, the filter then discards every candidate that does not belong to the requesting tenant, and whatever survives is returned. If a tenant owns one percent of the rows, roughly one percent of the candidate window survives, and a request that asked for ten results receives three or four with no error and a perfectly ordinary looking response.

What makes this dangerous is that it degrades with scale rather than failing at a threshold. During development every tenant owns a large fraction of a small table, so the window is mostly relevant and everything looks correct. The symptom appears months later when one tenant has grown large enough to crowd the others out, and it appears as a quality complaint rather than an error: someone says search has got worse, and nothing in the logs or the metrics disagrees with them, because every request returned a successful status with a plausible payload.

The fix that actually works is to make the index keep walking until it has enough rows that survive the filter, rather than walking a fixed distance and hoping. Most implementations expose this as an iterative or streaming scan mode, and the important detail is choosing the variant that preserves distance ordering. The relaxed variant is faster but may emit rows slightly out of order, which matters enormously when a limit is applied: a row just outside the true best ten can be emitted before one inside it, and the limit then cuts the better row. Measured recall was indistinguishable between the two modes on our data, so the ordering guarantee cost nothing and we took it.

Widening the initial candidate window is the obvious alternative and it is mostly a trap. It does help, but it helps by making the window large enough that the post-filter still leaves enough rows, which means the required width is a function of how skewed tenant sizes are and has to be re-tuned every time that skew changes. It also costs buffers on every single query, including the overwhelming majority that never needed the extra width. We measured the iterative scan at the default window recovering the full result set on twenty of twenty probe queries, identical to a window five times wider at roughly half the buffer reads, so the wider window was simply paying for nothing.

One genuinely useful variant is worth knowing about. If the filter column has low cardinality and the skew is permanent, a partial index per tenant turns the filter into an index condition rather than a post-filter, which removes the problem at the root instead of working around it. That trades write cost and index count for query predictability, and it only pays when the tenant set is small and stable.
