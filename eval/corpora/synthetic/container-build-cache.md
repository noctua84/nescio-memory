---
name: Container image build cache and dependency layer ordering
description: Why the build spends minutes reinstalling unchanged dependencies, the layer ordering rule that fixes it, and the lockfile copy trick that makes the cache survive source edits.
type: reference
---
A build is a sequence of layers and each layer is cached against the exact inputs that produced it. The cache for a layer is valid only if every layer before it was also a cache hit, which is the single most important property to internalise, because it means one early miss invalidates everything downstream no matter how unrelated. This is why a one-character change to a source file can cost a full dependency reinstall: if the source files are copied in before the dependencies are installed, then changing any source file invalidates the copy layer, and the install layer after it must be rebuilt even though nothing it depends on changed.

The ordering rule that follows is to put the slowest and least frequently changing work earliest. Concretely, copy only the dependency manifest and lockfile, install dependencies, and only then copy the rest of the source. Now an ordinary source edit invalidates only the final copy and whatever comes after it, while the install layer stays cached until the lockfile itself changes, which is when a reinstall is genuinely necessary. This is a two line change in most builds and it routinely takes a multi-minute build down to a handful of seconds.

The detail people miss is that the manifest copy has to be narrow. Copying the whole directory and then installing defeats the purpose entirely, because the copy layer now depends on every file. If your dependency manifest lives next to files that change constantly, copy it explicitly by name rather than by directory.

Multi-stage builds interact with this in a way that is useful once understood. A stage that is not the final stage still gets cached, so a build stage that compiles dependencies can be cached independently of the runtime stage that copies the result, and the runtime image stays small because the build toolchain never enters it. The caveat is that intermediate stages are not pushed to a registry by default, so a continuous integration runner with no local cache gets no benefit from them. If builds run on ephemeral runners, the cache has to be exported somewhere shared and imported at the start of the build, and that import has to include the intermediate stages or the dependency layer is rebuilt every time.

Two further traps. First, any instruction that embeds a changing value, such as a timestamp or a commit identifier, invalidates its own layer and everything after it, so these belong as late in the file as possible and ideally as metadata rather than as build arguments consumed early. Second, a package manager that writes a cache into the image will either bloat the image or, if cleaned in a later layer, bloat it anyway because the earlier layer still contains the files. Clean within the same layer that created them, or use a cache mount that is not committed to the image at all.
