---
name: Idempotency keys for write endpoints and the response replay rule
description: How a client-supplied key makes a retried write safe, why the stored response must be replayed rather than recomputed, and the concurrent-retry race the fingerprint check closes.
type: reference
---
Every write endpoint that a client might retry accepts a client-generated key, and a request carrying a key that has been seen before returns the original response rather than performing the operation again. The client is responsible for generating the key and for reusing the same key across retries of what it considers one logical operation, which is the part most client implementations get wrong: generating a fresh key on each retry attempt is indistinguishable from making several distinct requests, and the server has no way to tell the difference.

The stored response is replayed verbatim, including its status code and body, and it is not recomputed. This matters more than it sounds. If a retry re-ran the read path to build a fresh response, the client would receive a representation of the resource as it is now rather than as it was when the operation succeeded, and any change made in between would surface as an inexplicable difference between two responses to what the client believes is one request. Replaying the original also means the retry costs almost nothing, which is the behaviour you want when a client is retrying because the system is already struggling.

Keys are scoped to the authenticated client and to the endpoint, so two clients cannot collide and one client reusing a key against a different endpoint is treated as a new operation rather than as a replay. Expiry is twenty-four hours, which comfortably exceeds any retry schedule we expect and bounds the storage.

The race that needs care is a concurrent retry rather than a sequential one: two attempts arriving close enough together that the first has not finished recording its result when the second arrives. Handling this requires the key record to be claimed before the work begins rather than written after it, so the second attempt finds an in-flight claim and can wait or return a conflict rather than performing the operation a second time. We return a conflict with a retry hint, because waiting holds a connection for the duration of an operation that is already slow enough to have been retried.

The fingerprint check exists for a different failure. A client that reuses a key for a genuinely different request, usually by caching the key too broadly, would otherwise receive the stored response for an operation it did not ask for, which is far worse than an error. So a hash of the canonical request body is stored with the key, and a key presented with a body that does not match its fingerprint returns an error naming the mismatch rather than replaying. Two notes on the hash: it must be computed over a canonical form, since a re-serialised body with reordered fields is the same request, and it must exclude any field the client legitimately varies between retries, a timestamp being the usual culprit.
