---
name: Data retention windows and the deletion propagation checklist
description: How long each category of record is kept, why backups are treated separately from live data, and the subsystems that a deletion request has to reach to actually be complete.
type: policy
---
Retention is set per category of data rather than per table, because the obligation attaches to what the data is about rather than to where it happens to be stored. Account records are kept for the life of the account plus thirty days. Transaction records are kept for seven years, which is the longest window we carry and is driven by financial record keeping obligations rather than by any product need. Request and application logs are kept for ninety days. Behavioural analytics events are kept for thirteen months, which allows a year-over-year comparison with a month of margin. Anything not covered by a category defaults to the shortest window, ninety days, and the default is deliberately aggressive so that an uncategorised new data flow becomes visible rather than accumulating quietly.

Backups are governed separately and this separation is the single most commonly misunderstood part of the policy. Deleting a record from the live system does not remove it from a backup taken before the deletion, and rewriting backups to remove individual records is not technically feasible in any way we would trust. The position is therefore that backups have their own retention, thirty-five days for daily snapshots and twelve months for monthly ones, and a deleted record may persist in a backup until that backup ages out. This is a defensible position precisely because the backup window is bounded and documented, and it stops being defensible the moment someone keeps a backup indefinitely for convenience.

The restore rule follows from that and is not optional: if a backup is restored, the deletions that were applied after that backup was taken must be reapplied. There is a deletion journal recording the identity and timestamp of every erasure specifically so that this is mechanical rather than a reconstruction.

A deletion request is not complete when the row is gone, and this checklist exists because our first few were not. The live database row goes first. The search index holds a copy and must be purged explicitly, because index deletion is asynchronous and a document can remain queryable for some minutes after its source is gone. The object store holds any uploaded files, which are keyed by identifier and will not be found by any query that looks for the account. The analytics warehouse holds a copy that arrived through the event pipeline and is not reached by anything that touches the operational database. The email and messaging provider holds contact records and message history under its own retention, which has to be requested through its interface. Any third party that received the data under a processing agreement has to be notified, and the list of those is maintained alongside this document.

The last two are the ones that get missed, consistently, and both are outside our infrastructure, which is exactly why. Treat the checklist as the definition of done rather than as a reminder.
