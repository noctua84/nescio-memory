---
name: Infrastructure state locking and recovering from a stale lock
description: How the remote state lock works, the exact circumstances under which a lock is left behind, and the safe recovery procedure including what to verify before forcing anything.
type: runbook
---
State is stored remotely and every operation that could write it takes a lock first. The lock is a separate record holding who took it, when, and what operation they were running, and the reason it exists is that two concurrent applies against one state file can interleave their writes and produce a state that describes neither the infrastructure that existed before nor the one that exists after. Recovering from that is genuinely difficult and has historically meant reconstructing state by importing resources one at a time.

A lock is released when the operation finishes, including when it fails cleanly. The cases where a lock survives are all cases where the process did not get to run its cleanup: a terminated continuous integration job, a laptop that went to sleep or lost its network mid-apply, a container killed for exceeding its memory limit. In every one of these the lock record is intact and correct, it simply describes an operation that is no longer running.

When you hit a stale lock the error tells you the identity, the timestamp and the operation. Read all three before doing anything, because the single most expensive mistake available here is forcing a lock that belongs to a run which is still going. The timestamp is the most useful field: a lock a few minutes old during working hours is very likely live, and a lock from yesterday is very likely not. If the identity points at a continuous integration run, go and look at whether that run is still executing; the pipeline history will tell you in seconds and is authoritative in a way that guessing is not.

Only once you have confirmed the holder is genuinely gone should you force the unlock, which takes the lock identity from the error message. What you must not do is work around the lock by pointing at a different state file, or by disabling locking for one run to get unblocked, both of which have been tried here and both of which traded a five minute delay for a multi-day reconstruction.

There is a worse case worth preparing for. If the interrupted operation was partway through writing state when it died, the lock is stale and the state may also be inconsistent with reality: resources were created but are not recorded, or are recorded but were destroyed. After forcing an unlock, always run a plan and read it properly rather than skimming it. A plan proposing to create something you believe already exists is the signature of this situation, and the remedy is to import the real resource rather than to let the plan create a duplicate. Remote state keeps versioned history, so rolling back to the previous state version is available and is sometimes cleaner than importing, but it is only correct if nothing has been successfully applied since.
