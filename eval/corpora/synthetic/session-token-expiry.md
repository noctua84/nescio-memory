---
name: Session token lifetime and the refresh rotation decision
description: Why access tokens are short lived with rotating refresh tokens, the reuse-detection rule that makes rotation worth the complexity, and the clock skew allowance.
type: decision
---
Access tokens live for fifteen minutes and refresh tokens for fourteen days, and the refresh token rotates on every use. Those three numbers were argued over for longer than they deserved, so the reasoning is written down here to stop it being relitigated every time someone finds the re-authentication prompt annoying.

The short access token lifetime is the only thing standing between a leaked token and indefinite access, because access tokens are deliberately not checked against any server-side store. That is what makes them cheap to validate: a signature check and an expiry comparison, no database round trip, which is why the authorisation path can run on every request without becoming the bottleneck. The price of that cheapness is that a leaked access token cannot be revoked, so the only control available is for it to stop working soon. Fifteen minutes is a judgement about how long an attacker with a stolen token should be able to act, balanced against how often a client has to spend a round trip refreshing.

Refresh tokens are the opposite shape. They are checked against a store on every use, so they can be revoked, and they are therefore allowed to live much longer. Rotation means each refresh returns a new refresh token and invalidates the one that was presented. The reason that is worth the extra complexity is reuse detection: if a rotated token is ever presented a second time, either an attacker has a stolen copy or a legitimate client has a copy it should no longer have, and in both cases the correct response is to invalidate the entire chain and force a fresh authentication. Without rotation, a stolen refresh token is good for its full fourteen days and nothing anywhere can tell that it has been stolen.

The failure mode rotation introduces is real and has bitten us. A client that fires two refresh calls concurrently will have one succeed and one present an already-rotated token, which looks exactly like theft and logs the user out. We handle this with a short grace window: a rotated token presented again within ten seconds returns the same replacement rather than triggering the alarm, and only a presentation after that window is treated as reuse. That window is a deliberate weakening and the number should not be raised casually, because its length is exactly how long a stolen token remains useful.

Clock skew gets thirty seconds of allowance on expiry checks in both directions, which exists because client clocks are wrong more often than anyone expects and a client with a fast clock will otherwise reject tokens that are perfectly valid. Thirty seconds is small enough not to meaningfully extend a leaked token's life and large enough to cover the skew we actually observe. Do not extend it to cover a specific misbehaving client; fix the client.
